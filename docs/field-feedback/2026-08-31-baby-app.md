# Harness feedback from the baby-care project — 2026-08-31

Field feedback from ~7 weeks of running a multi-agent development harness in production
(Claude Code CLI, background agents via the Agent tool). Setup: a thin owner-facing lead
session delegates each work wave to a fresh background "wave-lead" (Sonnet), which spawns
builder subagents and an Opus reviewer, merges, and reports back. Waves run long (hours),
often unattended, and survive laptop sleeps and API stream deaths. That shape has stress-
tested the harness's multi-agent lifecycle harder than interactive use does, and the same
gaps keep recurring. Issue numbers reference the project's tracker; each has full evidence.

## 1. Nested Agent spawn reliably kills the parent's stream (#569) — highest impact

A background agent that itself calls the `Agent` tool dies mid-turn at exactly that call.
Two consecutive fresh wave-lead sessions on 2026-08-26 died at the identical operation —
final transcript event `stop_reason=tool_use` on their first `Agent` spawn; the call never
executed (no tool result, no child transcript). Reproduced with both `run_in_background`
variants. Both sessions were healthy up to that point (150KB/82KB transcripts of normal
work). Top-level spawns from the interactive lead work fine.

This breaks the core delegation model (lead → wave-lead → builders): nesting is the whole
point of a wave-lead. Workarounds in use: lead-orchestrated waves (defeats the
context-thinning purpose), and adopting orphaned builders from dead wave-leads.
CLI version at reproduction: 2.1.222. Ask: a minimal-repro fix, or at least a documented
supported depth for background-agent nesting.

## 2. No death signal for a mid-turn-dead session (#569, #446, #312)

When a stream dies mid-turn the session stays "running" forever, burning nothing, firing
no hook, emitting no task notification. Nothing distinguishes it from a busy session
except transcript mtime. Consequences observed:

- We had to build our own liveness monitor (`wave-watchdog.sh`, a mtime poller) because
  no harness signal exists for this state.
- `SendMessage` to a mid-turn-dead session **silently no-ops** — the resume appears
  queued but nothing happens, so the sender can't tell resume-failed from slow-agent
  (confirmed during the 2026-08-26 incident, evidence on #446).

Ask: a harness-level liveness/death event for background agents (stream terminated
without turn completion), and an error or delivery status when SendMessage targets one.

## 3. Transcript-idle is the wrong liveness proxy for delegating agents (#596, #446)

Our mtime watchdog false-positives on exactly the sessions it exists to protect: a
wave-lead's own transcript legitimately goes idle for 20+ minutes whenever it delegates
(blocked on a synchronous child, or waiting on background children). Three documented
false alarms (2026-08-15, 2026-08-29, 2026-08-31 — the last one fired while three builder
children were actively writing). The fix we converged on: all-stale semantics over the
session's whole subagent tree (newest mtime across `subagents/agent-*.jsonl`, re-globbed
each tick so mid-wave children are picked up). If the harness grew native liveness
(item 2) this whole class of DIY monitoring disappears; failing that, tree-level idle
would be the right built-in.

## 4. Zombie resume / resume-vs-respawn races (#446) — worst realized incident

On 2026-08-15 a wave-lead believed dead (per item 3's false detection) was queued a
resume message AND replaced with a fresh session. The "dead" session later woke, consumed
the stale "resume and continue" instruction, and raced its replacement: merged PRs at
pre-fix heads (temporarily dropping two HIGH security fixes from main), cut and
distributed a release, and deployed unreviewed code to a live gateway. A milder rerun on
2026-08-26: a wave-lead zombie-revived mid-wave and spawned duplicate Opus reviewers on
two PRs (reconciled without lost work, but pure waste).

Asks: (a) fencing primitive — respawning a replacement should be able to invalidate the
old session id so a later wake becomes a no-op; (b) stale-message expiry or at least a
"queued N hours ago" marker on delivery, so a woken session doesn't act on instructions
whose context has moved on.

## 5. TaskStop has no drain semantics (#446)

TaskStop landed while a session was mid `docker-compose` bring-up on a home server; the
kill left the server in a mixed state that took two follow-up sessions to characterize.
For agents known to run infra side-effects, a stop should support (or at least offer)
drain-to-safe-point / a final checkpoint turn, rather than hard kill only.

## 6. No provenance on inter-agent messages (#446)

Agents cannot distinguish a genuine lead/owner message from injected text. We've hit both
failure directions within two days: real lead messages dismissed as injection probes
(2026-08-14), and a real rollback order declined as "fabricated" (2026-08-15 — arguably
the procedurally correct paranoia, but the harness forces every agent to hand-roll that
judgment). Ask: an authenticated channel or harness-signed marker for parent→child
traffic, so "this really came from your spawner" is machine-checkable, not vibes.

## 7. Concurrent sessions share one mutable working tree by default (#359)

Multiple sessions (waves, checkpoints, ad hoc lead work) mutate the same checkout unless
each opts into a worktree. Observed: a release wave found the shared root occupied by a
foreign session's live conflicted rebase (detached HEAD, unmerged paths) for the wave's
entire duration; and the item-4 zombie race was this risk realized on `main` itself.
Convention-level fix in use (per-agent worktrees); the ask is default isolation — e.g.
background agents get `isolation: worktree` semantics by default when the cwd is a git
repo, or a first-class advisory lock the harness checks before git-mutating operations.

## 8. What has worked well (keep it)

- **Durable-state-first recovery**: a wave on 2026-08-29 survived an API stream death AND
  a 2-hour laptop sleep that killed 5 child sessions, because state lives in PRs,
  branches, worktrees, and issue comments — a fresh session reconstructed and finished
  the wave. Harness features that encourage externalized state are the right bet.
- **Background-agent completion notifications**, when they fire, make the lead-as-
  dispatcher model work with near-zero polling.
- **Task output files as inspectable transcripts** (symlinked JSONL) made every postmortem
  above possible; please never remove filesystem-visible transcripts.

## Summary of asks, priority order

1. Fix nested background-agent → Agent spawn stream death (#569).
2. Native death/liveness signal for background agents + SendMessage delivery status (#446/#569).
3. Session fencing for resume-vs-respawn, and stale-message age marking (#446).
4. Drain/checkpoint semantics on TaskStop for side-effectful agents (#446).
5. Signed/authenticated parent→child message provenance (#446).
6. Default git isolation (worktree) or advisory locking for concurrent sessions (#359).
7. If liveness stays DIY: tree-level (all-children) idle detection guidance instead of
   single-transcript mtime (#596).
